GitHub Actions 캐시

매번 4분 걸리던 Gradle 빌드가 40초가 됐습니다. 바꾼 건 캐시 키 몇 줄입니다. 숫자는 예제 저장소 기준입니다.

무엇이 느렸나

GitHub Actions의 러너는 실행할 때마다 새 머신입니다. 캐시가 없으면 매 실행마다 의존성을 전부 다시 내려받습니다. 예제 저장소에서는 이 다운로드가 3분이었고, 실제 컴파일과 테스트는 40초였습니다. 느린 건 빌드가 아니라 다운로드였습니다.

actions/cache 키 설계

 steps:
   - uses: actions/checkout@v4
+  - uses: actions/cache@v4
+    with:
+      path: |
+        ~/.gradle/caches
+        ~/.gradle/wrapper
+      key: gradle-${{ runner.os }}-${{ hashFiles('**/*.gradle*', 'gradle/wrapper/gradle-wrapper.properties') }}
+      restore-keys: gradle-${{ runner.os }}-
   - run: ./gradlew build --no-daemon

두 줄이 전부입니다.

  • key는 정확히 일치할 때만 복원됩니다. hashFiles에 의존성 선언 파일을 넣어서, 의존성이 바뀌면 키가 바뀌고 새 캐시가 만들어지게 합니다.
  • restore-keys는 접두사 일치 fallback입니다. 정확한 키가 없어도 가장 최근의 gradle-Linux- 캐시를 가져옵니다. 의존성 하나가 바뀌었을 때 나머지 99개를 다시 받지 않게 해 주는 장치입니다.

캐시가 안 맞을 때 확인할 것

  • 로그에서 Cache restored from key: 줄을 찾으세요. 없으면 키가 안 맞는 겁니다. 어떤 키로 찾았는지도 그 위에 찍힙니다.
  • hashFiles 패턴이 실제 파일을 가리키는지 확인하세요. 패턴이 아무것도 못 찾으면 해시가 빈 값이 되어 키가 늘 같아지고, 의존성이 바뀌어도 오래된 캐시를 계속 씁니다.
  • 브랜치 범위. PR 브랜치는 기본 브랜치의 캐시를 읽을 수 있지만 반대는 안 됩니다. 캐시는 main에서 한 번 만들어져야 합니다.
  • 저장소당 캐시 한도(10GB)를 넘으면 오래된 것부터 지워집니다. 큰 캐시를 여러 키로 만들면 서로 밀어냅니다.

devgrr 리뷰 코멘트 build.yml:5

setup-java의 cache: gradle 옵션 한 줄로 같은 걸 얻을 수 있습니다. 직접 actions/cache를 쓰는 건 키를 내 마음대로 설계해야 할 때만. 먼저 쉬운 길이 있는지 확인하는 습관이 4분을 아낍니다.

steps:
  - uses: actions/checkout@v4
  - uses: actions/setup-java@v4
    with:
      distribution: temurin
      java-version: 21
      cache: gradle
  - run: ./gradlew build --no-daemon

정리

  • 느린 건 빌드가 아니라 다운로드일 때가 많습니다. 먼저 어디서 시간이 가는지 보세요.
  • key는 의존성 파일의 해시로, restore-keys는 접두사 fallback으로.
  • 공식 setup 액션의 cache 옵션이 있으면 그것부터.
