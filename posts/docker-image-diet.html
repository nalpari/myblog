Docker 이미지 다이어트

1.2GB짜리 Spring Boot 이미지가 180MB가 되기까지 한 일은 세 가지뿐입니다. 순서가 중요합니다. 크기는 예제 프로젝트 기준이고, 여러분 프로젝트에서는 숫자가 다를 겁니다.

왜 1.2GB였나

처음 Dockerfile은 정직하게 다 담았습니다. JDK가 들어 있는 풀 이미지 위에 소스 전체를 복사하고, 그 안에서 빌드했습니다. 결과물에는 JDK, 소스, Gradle 캐시, 테스트 리포트까지 빌드 부산물이 전부 남습니다.

FROM eclipse-temurin:21
WORKDIR /app
COPY . .
RUN ./gradlew bootJar
ENTRYPOINT ["java", "-jar", "build/libs/app.jar"]

어느 레이어가 큰지는 추측하지 말고 물어보세요. docker history가 레이어별 크기를 보여 줍니다.

docker history myapp:before --format "{{.Size}}\t{{.CreatedBy}}" | head

1. 멀티 스테이지: 빌드 환경과 실행 환경을 나눈다

실행할 때 필요한 건 JRE와 jar 하나뿐입니다. 빌드 단계와 실행 단계를 나누면 JDK, 소스, Gradle 캐시는 첫 단계에 남고 버려집니다.

-FROM eclipse-temurin:21
-WORKDIR /app
-COPY . .
-RUN ./gradlew bootJar
+FROM eclipse-temurin:21 AS build
+WORKDIR /app
+COPY gradlew build.gradle settings.gradle ./
+COPY gradle ./gradle
+RUN ./gradlew dependencies --no-daemon
+COPY src ./src
+RUN ./gradlew bootJar --no-daemon
+
+FROM eclipse-temurin:21-jre
+WORKDIR /app
+COPY --from=build /app/build/libs/app.jar app.jar
 ENTRYPOINT ["java", "-jar", "app.jar"]

이것만으로 1.2GB가 300MB 근처로 내려옵니다. 대부분의 무게는 JDK와 빌드 부산물이었습니다.

2. 레이어 순서: 잘 안 바뀌는 것부터

Docker는 위에서부터 레이어를 캐시하고, 한 레이어가 바뀌면 그 아래는 전부 다시 만듭니다. 의존성 선언(build.gradle)을 소스보다 먼저 복사하면, 소스만 바뀐 빌드에서는 의존성 다운로드 레이어를 그대로 재사용합니다. 이건 이미지 크기보다 빌드 시간에 크게 듣습니다. 위 diff에서 COPY src가 dependencies 뒤에 오는 이유입니다.

3. alpine을 고르기 전에 확인할 것

21-jre-alpine으로 바꾸면 180MB 근처까지 내려갑니다. 하지만 alpine은 glibc 대신 musl을 씁니다. 네이티브 라이브러리를 쓰는 의존성(일부 압축, 암호화, 이미지 처리 라이브러리)이 있으면 여기서 깨집니다. 바꾸기 전에 두 가지를 확인하세요.

  • 앱이 네이티브 의존성을 쓰는지. jar tf app.jar | grep -E "\.so$"로 대략 알 수 있습니다.
  • 타임존과 로케일. alpine에는 tzdata가 없어서 Asia/Seoul이 안 잡힐 수 있습니다. 필요하면 apk add tzdata.

이미지 크기는 목표가 아니라 결과입니다. 먼저 docker history로 어느 레이어가 큰지 보세요. 숫자 없이 alpine부터 바꾸면 원인도 모른 채 호환성 문제만 얻습니다.

정리

  • 멀티 스테이지 빌드: JDK와 빌드 부산물을 실행 이미지에서 뺀다. 가장 큰 효과.
  • 레이어 순서: 의존성 선언을 소스보다 먼저 복사한다. 빌드 시간에 효과.
  • alpine: 네이티브 의존성과 타임존을 확인한 뒤에 고른다.
