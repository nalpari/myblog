useEffect 정리

cleanup 함수는 "컴포넌트가 사라질 때" 실행되는 게 아닙니다. 의존성이 바뀔 때마다, 다음 effect가 실행되기 직전에 실행됩니다. 이 순서를 알면 무엇을 정리해야 하는지가 보입니다.

타임라인으로 보기

[id]에 의존하는 effect가 있고, id가 1에서 2로 바뀐 뒤 컴포넌트가 사라진다고 해 봅시다.

  1. 마운트: effect(id=1) 실행
  2. id가 2로 변경: cleanup(id=1) 실행, 그다음 effect(id=2) 실행
  3. 언마운트: cleanup(id=2) 실행

cleanup은 "이전 effect의 뒤처리"입니다. 언마운트는 그 특수한 경우일 뿐입니다. 그러니 cleanup 안에서는 언마운트를 가정하지 말고, "방금 전 effect가 만든 것"만 치우면 됩니다.

그래서 무엇을 정리해야 하나

effect가 만든 것 중 시간이 지나도 살아 있는 것들입니다. 타이머, 구독, 이벤트 리스너, 그리고 진행 중인 요청. 요청이 가장 자주 빠집니다.

 useEffect(() => {
   const controller = new AbortController();
   fetch(`/api/users/${id}`, { signal: controller.signal })
     .then((r) => r.json())
     .then(setUser);
-}, [id]);
+  return () => controller.abort();   // id가 바뀌면 이전 요청부터 취소
+}, [id]);

id가 1에서 2로 빠르게 바뀌면, 1의 응답이 늦게 도착해 2의 화면을 덮어쓸 수 있습니다. 경쟁 상태(race)입니다. 이전 effect의 cleanup에서 요청을 취소하면 늦은 응답은 버려집니다. 타이머도 같은 모양입니다.

useEffect(() => {
  const timer = setInterval(() => setNow(Date.now()), 1000);
  return () => clearInterval(timer);   // 정리하지 않으면 타이머가 겹겹이 쌓인다
}, []);

개발 모드 StrictMode에서 effect가 두 번 실행되는 건 버그가 아니라 검사입니다. cleanup이 제대로 돼 있으면 두 번 실행돼도 결과가 같아야 하니까요. 두 번 실행돼서 문제가 생긴다면 그건 cleanup이 없다는 신호입니다.

정리

  • cleanup은 의존성이 바뀔 때마다, 다음 effect 직전에 실행됩니다. 언마운트는 그중 하나입니다.
  • 정리 대상은 타이머, 구독, 리스너, 진행 중인 요청. 요청은 AbortController로 취소합니다.
  • StrictMode의 두 번 실행은 cleanup을 검사하는 장치입니다.
